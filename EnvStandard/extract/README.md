# 抽取层原型：从检测报告 PDF 抠出规则引擎能吃的字段

## 它在整条链里的位置

```
检测报告 PDF
     ↓  ★本目录：语义抽取 + 容错校验
   items[]（结构化）
     ↓  ../engine：规则终审（只吃字面与数值比对，不调模型）
   findings（逐条带出处）
```

## 最要紧的一条设计原则

**抠不出来就说抠不出来。**

每个字段都可能返回 `null` + 一条 `pending` 说明缺什么，**绝不用一个「看起来合理」的值填上**。
原因：下游规则引擎的判定完全依赖这些字段 —— 一个猜出来的 `basis`（评价口径）
会让「限值核对」整条规则**静默失效**，比直接报错糟得多。

这条原则在三个地方都验证过：

| 场景 | 行为 |
|---|---|
| 脚注不写标准号与评价口径 | `basis`/`standard` 全为 `null`，逐项写明缺什么 |
| 一节列了 3 个方法但不说哪个因子用哪个 | 不代猜分配，标未定并列出这 3 个方法 |
| 结论措辞既不像达标也不像超标 | 返回 `null` 而不是默认判成达标 |

## 目录

```
extract.py            抽取层主体（规则驱动，确定性，不调模型）
variants.py           降级变体构造（降级测试与端到端共用）
test_degrade.py       降级测试：依据缺失 / 措辞不同 / 扫描件
test_e2e.py           端到端：PDF → 抽取 → 引擎 → 结论
sample/
  sample-report.html  构造报告（结构上还原真实报告的难点）
  sample-report.pdf   打印成 PDF（有文本层）—— 这是测试夹具，入库
  ground-truth.json   正确答案
  variants/           降级变体 —— **生成物，不入库**（.gitignore）
```

`variants/` 是生成物：降级测试与端到端测试会**按需生成**，
所以直接跑任一测试即可，不必先跑另一个。

配套工具在 `../tools/`：`make_sample_report.py`（造报告）、`print_pdf.mjs`（打 PDF）。

## 用法

```bash
python extract.py sample/sample-report.pdf            # 看抽出了什么
python extract.py sample/sample-report.pdf --json     # 给引擎吃
python extract.py sample/sample-report.pdf --score    # 与真值比对，出准确率
python test_degrade.py                                # 降级测试
python test_e2e.py                                    # 端到端
```

依赖：`pypdf`（抽文）、`pypdfium2`（仅降级测试里模拟扫描件用）。
请装在隔离环境里，不要污染全局。

## ⚠ 那个 100% 说明不了什么

在构造报告上字段准确率是 **100%（49/49）** —— 但这**只证明管道通**，
**不证明真实报告上也能到 100%**。原因很直接：**这份报告是我自己造的**，
它的表格是规则的、每行一行文本、脚注规规矩矩。

真实报告里已知存在、而这里**没有覆盖**的情况：

| 真实世界的问题 | 本原型的状态 |
|---|---|
| 表格跨页、表头重复 | ❌ 未测 |
| 合并单元格导致抽文顺序错乱 | ❌ 未测 |
| 扫描件（盖章、手写原始记录、拍照页） | ❌ 明确拒绝，不处理 |
| 单位写在表头而非每行 | ⚠ 本样本是每行都写；表头单位的解析未实现 |
| 结果写「未检出」「<0.05」 | ⚠ 已实现解析，但未测真值比对 |
| 一份报告里同一因子用不同方法 | ⚠ 靠「不代猜」兜住，但没测 |
| 报告用图片贴表格 | ❌ 抽文直接为空 |

**所以下一步该做的不是继续优化这份构造报告上的分数，而是拿一份真实报告来跑。**
用真实报告跑出来的准确率才有决策价值；在那之前，「可行」只能说到
「管道可行、边界清楚」。

## 已知的降级行为（test_degrade.py 覆盖）

**V2 依据缺失** —— 脚注不写标准号与用地类型：
结构照抽（7 项、限值都在），但 `basis`/`standard` 全为 `null`，
每项写明「本节没有可识别的评价依据脚注」。
引擎接着报 `R-LIM-01` 无法判定、`error_count = 0` —— **不硬判、不误报**。

**V3 措辞不同** —— 结论写「符合/不符合」：
归一化成「达标/超标」，结果与真值一致。
⚠ 这里踩过一个坑：**中文否定式包含肯定式** —— 「不符合」含「符合」、「未超标」含「超标」。
用子串包含判断会全判错。现按**长词优先**逐条匹配。

**V4 扫描件** —— PDF 没有文本层：
明确拒绝并说明原因，不吐半截结果。

## 端到端测试抓出来的真 bug（单层测不出来）

**① 引擎把「1」和「1.0」判成抄错。**
`R-LIM-01` 原来用 `str()` 比较限值 —— 报告写 1.0、标准是 1，被判成「限值抄错」。
三个假阳性。已改为数值比较。

**② 抽取层数不出「本节有几个方法」。**
原来拿 `STD_ALIAS`（已入库标准别名表）的键去匹配脚注 ——
**没入库的方法号会隐身**，于是「本节有 3 个方法」被判成 1，
抽取层就把唯一那个绑到所有因子上，引擎随即报「HJ605 中没有砷的检出限」。
已改为正则匹配标准号（不依赖别名表）。

**③ 引擎分不清「报告没写标准号」与「报告写了库里没有的标准号」。**
两者原来都报 error。前者是**抽取层没抽到**（未定），后者才是**报告的问题**（错）。
报错会掩盖真正的缺失。已区分。

**④ 抽取层标出的原因在传给引擎时丢了。**
引擎只说「未声明所用方法标准」，而抽取层其实知道原因
（「报告列出 3 个方法却没说是哪个因子用哪个」）。
已做透传：未定项带上「抽取层备注」。

这四条都是**两层接起来才暴露**的 —— 单独测抽取层、单独测引擎，全绿。

## 下一步

1. **拿真实报告跑** —— 这是唯一能给出真实准确率的事。在此之前不要基于构造样本下结论。
2. **补表头单位解析** —— 真实报告的表格常把单位写在表头。
3. **跨页表格** —— 表头重复时的行归属。
4. **接模型做自由文本** —— 目前全是确定性规则；真正需要模型的是
   「一段自由文字里这句话是什么意思」这类（如：报告正文里用自然语言描述评价依据）。
   结构抽取能用代码定的，就不要交给模型。
