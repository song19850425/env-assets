# EnvStandard 规则终审引擎

**把标准数据层从「给人看」变成「给机器调用」。**

这是「标准引用核查 / 报告审核」类工作流的**底座**：输入一份报告摘要，
输出逐条带出处的核查结论。三个候选产品（标准引用核查、报告审核、合规体检）都建在它上面。

## 为什么单独做一层引擎

政策/法规类文档的解析，最容易犯的错是**让规则层也去调模型** ——
那规则层就成了模型的马甲，二次校验形同虚设。

所以这里严格照三层架构，本目录只做**第三层**：

```
文档 → 语义抽取(LLM，另做) → 容错校验(另做) → ★规则终审(本目录) → 证据链
```

| 层 | 谁做 | 关键约束 |
|---|---|---|
| 语义抽取 | LLM | 允许留空、允许标存疑、**禁止强归** |
| 容错校验 | 代码 | 宁可丢证据，不可留假证据 |
| **规则终审** | **本目录** | **只吃字面与数值比对，绝不调模型** |

## 三条设计原则

**① 规则是数据，不是代码。**
规则写在 `rules.json` 里，改规则不动引擎，便于 diff、审计和非技术人员维护。

**② 判据只从标准数据取，不另存一份。**
所有限值、检出限、保存时限都从 `../data/standards/*.json` 现读。
标准数据更新，引擎自动跟着变 —— 不会出现「页面写一套、引擎写另一套」。

**③ 判定不出来就说判定不出来。**
输出 `UNDETERMINED` 并写明缺什么，**不猜、不放过**。
最典型的例子：单位不一致时拒绝比大小 ——
拿 μg/L 的测定下限去比 mg/kg 的限值，数值上「成立」但结论毫无意义。

## 现有规则

| 规则 | 查什么 | 级别 |
|---|---|---|
| R-STD-01 | 引用的标准号必须已入库 | error |
| R-STD-02 | 引用标准必须声明到条款/表格级 | warn |
| R-LIM-01 | 报告写的限值必须与标准值一致 | error |
| R-LIM-02 | 达标结论必须与检测值和限值一致 | error |
| R-MDL-01 | 所选方法的测定下限必须低于所判定的限值 | error |
| R-HOLD-01 | 样品保存时间不得超过标准规定 | error |
| R-QC-01 | 每批样品必须做空白 | error |
| R-QC-02 | 平行样比例不得低于标准规定 | warn |

**R-MDL-01 是唯一需要跨标准推论的规则**，也是通用 AI 答不出来的那一条：
把「限值」和「方法能力」放在一起比。例：四氯化碳 Ⅲ 类限值 2.0 μg/L
**低于** HJ 639 全扫描方式测定下限 6.0 μg/L → 该指标必须改用 SIM 方式（1.6 < 2.0）。

## 用法

```bash
python check.py samples/report-ok.json          # 文本报告
python check.py samples/report-bad.json --json  # JSON（供上层调用）
python test_engine.py                           # 自测（27 项断言）
```

退出码：`0` = 没有 error；`1` = 有 error。可直接进 CI。

## 输出长什么样

```
报告：DEMO-BAD-001  某地块土壤与地下水检测报告摘要（构造样本 · 含植入错误）
状态：FAIL  可核查程度：LOW  错误 6 · 无法判定 4

  ✗ [R-LIM-01] 报告写的限值必须与标准值一致（苯（soil））
      限值抄错：报告写 2.2，标准是 1（第一类用地筛选值）
      证据：标准=GB36600-2018；列=第一类用地筛选值；标准值=1；报告写的=2.2；
            出处=GB36600-2018 表 1 建设用地土壤污染风险筛选值和管制值（基本项目）（序号 26）
```

输出的是**可核查状态**（PASS / PARTIAL / FAIL + confidence_band），
不是「可信度 95%」这类无法验证的话。

## 输入格式

见 `samples/`。核心是 `items[]`，每项声明：
因子 / 介质 / 判定标准 + **basis（取哪一列）** / 报告写的限值 / 检测值 / 结论 / 所用方法。

`basis` 是关键 —— 它决定从标准的哪一列取限值：

```json
{ "landUse": "first", "kind": "screening" }   → GB 36600 第一类用地筛选值
{ "classLevel": "III" }                        → GB/T 14848 Ⅲ 类
```

不声明 `basis` 就取不到限值，引擎会如实报「无法定位限值列」，不会替你猜。

## 自测覆盖

- 干净样本**不报 error**（防误报）
- 植入的 6 处错误**逐条被对应规则抓到**（防漏报），含真实历史错误「苯限值写成 2.2」
- 单位不一致 → `UNDETERMINED` 而不是硬比大小
- 同一因子出现两次 → 两条结论各自独立，不互相覆盖
- 证据链含标准值、报告值、条款出处
- 缺字段 / 非数值 / 空文档 → 不崩，如实报无法判定
- **反向测试**：删掉一条规则后该规则不再报错，但相邻规则仍独立生效

## 单位换算：同量纲必须能比

R-MDL-01 要拿「方法的测定下限」比「标准的限值」，而两者常不在同一量级：
HJ 605 的检出限以 **μg/kg** 计，GB 36600 的筛选值以 **mg/kg** 计。
早期版本见单位串不同就直接报「无法判定」—— 太严，最常见的土壤场景反而判不了。

现在分三种情况：

| 情况 | 处理 |
|---|---|
| 同量纲（mg/kg ↔ μg/kg、mg/L ↔ μg/L、mg/m³ ↔ μg/m³、μmol/mol ↔ mmol/mol） | **换算后比较**，证据里写明换算过程 |
| 不可通约（μg/L vs mg/kg —— 分母一个是体积一个是质量） | 报 `UNDETERMINED`，并提示「给土壤样品引水质方法本身可能就是错的」 |
| 未知单位（如 NTU） | 报 `UNDETERMINED`，不瞎比 |

`μ` 的两种码位（U+00B5 微符号 / U+03BC 希腊字母 mu）在归一化时统一 —— PDF 字体子集不同会混用。

## 还没做的（下一步）

- **语义抽取层**：已建原型，见 [`../extract/`](../extract/)。
  在构造报告上字段准确率 100%，但**那证明不了真实报告上的准确率** ——
  报告是自己造的。真实世界的跨页表格、合并单元格、表头单位、扫描件都还没覆盖。
  **下一步应该拿一份真实报告跑，而不是继续优化构造样本上的分数。**
- **更多规则**：报告模板必备字段、三级审核留痕、方法适用范围与介质匹配、检出限与限值的批量比对。
- **继续补库**：标准库从 23 份增到 24 份（补入 HJ 605-2011 后，
  「土壤 VOCs 的方法能力」已可核对）。同类仍缺的常见方法标准：
  HJ 828-2017（COD）、HJ 636-2012（总氮）、HJ 670-2013（总磷）、
  HJ 491-2019 / HJ 680-2013（土壤重金属）、HJ 618-2011（PM2.5 重量法）。
  补库工具见 `../tools/`（从官方 PDF 程序化解析，不手抄）。

## 补库顺带修掉的一个既有数据错误

补 HJ 605 时发现 `pollutant-ids.json` 里 GB 5749-2022 的两条映射**写反了**：

| 中文名 | 原映射 | 正确 |
|---|---|---|
| 一氯二溴甲烷 | `bromodichloromethane` ✗ | `dibromochloromethane`（CAS 124-48-1） |
| 二氯一溴甲烷 | `dibromochloromethane` ✗ | `bromodichloromethane`（CAS 75-27-4） |

中文命名按「取代基个数」直译，与英文词序**相反**：一氯二溴甲烷 = 1 Cl + 2 Br = CHClBr₂。
交叉验证：GB 5749 限值 一氯二溴甲烷 0.1 / 二氯一溴甲烷 0.06，
与 WHO 指导值 dibromochloromethane 0.1 / bromodichloromethane 0.06 一致。
已修正（`tools/wire_hj605.py` 的 `FIXUPS`）。
