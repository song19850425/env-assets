# 环保资金申报指南识别 Agent｜架构评审报告

**评审对象**：LLM语义抽取 + JEV硬规则二次终审 架构方案
**适用范围**：国家级 / 省级生态环境专项资金申报指南
**评审日期**：2026-09-23
**结论**：架构方向正确，原方案存在 4 类可致漏报与不可复现的缺陷，已定位并修复 3 类；剩余 1 类需持续扩池。

---

## 一、总体判断

原方案的核心思路 —— **LLM 只做抽取、规则做终审** —— 是正确且必要的。政策文本解析场景下，纯 LLM 归类必然产生幻觉与错分，引入规则层作为终审是商用级架构的标准做法。

但原方案存在一个根本问题：**宣称的"规则终审"在实现层面仍是语义判断的马甲**。规则条件依赖 LLM 的语义理解（如"无水体治理目标"），规则层与语义层共用同一判断源，不构成独立的二次校验。此时输出"判定可信度 100%（规则终审通过）"是**不可验证的表述**。

本报告将其重构为**可执行规则 + 可追溯审计**的形态。

---

## 二、已定位缺陷与修复情况

### 缺陷 1｜标签池缺项导致系统性漏报 `已修复`

**现象**：原标签池仅七大类，且明令"不得自创标签"。而国家级与省级指南中，以下方向为独立章节，无法归入七大类：

| 缺失方向 | 实际指南中的呈现 |
| --- | --- |
| 应对气候变化 / 减污降碳协同 | 大气污染防治资金已分流出减污降碳协同专项 |
| 环境监测能力建设 / 智慧环保 | 能力建设类专项资金，与七大类并列 |
| 核与辐射安全 | 省级指南常见独立章节 |
| 环保产业 / 绿色金融配套（含 EOD） | 部分省份独立赛道 |

**后果**：命中即漏报。且"不得创造政策没有的项目类型"这条禁令与上述现实冲突时，模型只能丢标签，错误被静默吞没。

**修复**：标签池扩至 11 类（七大类 + CLIMATE / CAPACITY / NUCLEAR / INDUSTRY），并新增 `UNCERTAIN` 兑底标签与 `uncovered` 字段。语义层遇到标签池无法覆盖的内容**必须明说**，写入 `uncovered`，供人工判断是否扩池，而非硬塞进最接近的类别。

**落地点**：`system_prompt.md` 标签池定义、`jev_rules.json` 的 `labels`。

---

### 缺陷 2｜"规则终审"实为语义判断，不构成二次校验 `已修复`

**现象**：原规则形如：

> 强制归属：仅管网建设、**无水体治理目标** → 不打水环境主标

"无水体治理目标"的判定仍由 LLM 完成。规则层未独立于语义层，二次校验流于形式。

**修复**：规则改为**封闭词表命中制**，每条规则可写成布尔表达式，判定过程可 grep、可复现、可审计：

```json
{
  "id": "X-WATER-01",
  "label": "WATER",
  "all": ["管网"],
  "none": ["黑臭水体", "入河排污口", "水生态", "水质提升", "水体治理", "断面"],
  "note": "仅管网建设、无水体治理目标 → 不打水环境主标"
}
```

判定逻辑：`all` 全中 且 `any` 至少一中（若有） 且 `none` 全不中 → 排除规则生效。

**落地点**：`jev_rules.json` 的 FORCE / EXCLUDE 规则全部词表化；`jev_engine.py` 实现判定逻辑。

---

### 缺陷 3｜否定句被当肯定句使用 `已修复（最隐蔽）`

**现象**：这是实测中发现的最隐蔽缺陷。原规则库下，文本：

> "本项目实施雨污分流管网建设……**本项目不涉及河湖水体治理内容**。"

`管网` 命中 `F-WATER-04` 强制规则，而 `X-WATER-01` 排除规则的 `none` 词表包含"水体治理"，`"不涉及河湖水体治理内容"` 中的字面匹配让排除规则**未能生效**。结果：纯管网项目被打上 WATER 主赛道标签。

**根因**：政策文本中大量存在否定式表述（"不纳入""不得申报""不属于……范围"），纯字面匹配无法区分肯定与否定。这也是负面清单提取极易出错的同一根源。

**修复**：新增 `is_negated()` 判定。**否定作用域不跨句** —— 向前查找否定前缀时，在最近的句号 / 分号 / 换行处截断：

```
本项目不涉及管网。本次实施河湖水体治理。
                ↑ 句号截断        ↑ 不被否定 ✅
```

同一句内的并列成分共享否定作用域（"不涉及A和B" 中 B 也被否定）。命中即不计入词表命中，`negated` 字段留痕用于审计。

修复前后对比：

| 输入 | 修复前 | 修复后 |
| --- | --- | --- |
| 仅管网建设 + "不涉及河湖水体治理" | 主赛道 = 水生态水环境 ❌ | 主赛道 = 无，WATER 被剔除，留痕规则冲突 ✅ |

**落地点**：`jev_engine.py` 的 `NEGATION_PREFIXES` / `is_negated()` / `_present(skip_negated=True)`。

> 该缺陷在回归测试中被二次捕获：初版实现用 12 字符定长窗口，导致 `"本项目不涉及管网。本次实施河湖水体治理"` 中的「水体治理」被误判为否定（否定词跨越了句号）。改为句边界截断后修复。

---

### 缺陷 4｜权重规则互斥且无优先级声明 `已修复`

**现象**：原方案存在规则打架：

- "地下水 + 土壤共存 → 土壤为主" （权重规则）
- "非污染治理类工程 → 剔除土壤标签" （土壤排除规则）
- "河道治理 + 绿化 → 水环境为主、生态修复协同" （权重规则）
- "流域全域系统修复 → 强制山水标签，且纯单一污染治理不得打山水主标" （山水规则）

一个矿山修复项目若含地下水监测井与土壤治理，按权重规则该判土壤，按山水排除规则该剔除土壤，**两条规则互斥且无优先级声明**，实际结果取决于遍历顺序，不可复现。

**修复**：确立三级刚性优先级，写死在代码中：

```
EXCLUDE（一票否决） > FORCE（强制打标） > WEIGHT（主次裁决）
```

权重规则按**具体度排序**，最具体的组合前置，第一匹配生效：

| 规则 ID | 触发条件 | 主赛道 | 协同 |
| --- | --- | --- | --- |
| W-01 | MOUNTAIN + GROUNDWATER | MOUNTAIN | GROUNDWATER |
| W-02 | MOUNTAIN + SOIL | MOUNTAIN | SOIL |
| W-03 | RURAL + WATER | RURAL | WATER |
| W-05 | RURAL（任意组合） | RURAL | * |
| W-06 | GROUNDWATER + SOIL | SOIL | GROUNDWATER |
| W-07 | SOLID + SOIL | SOLID | SOIL |
| W-08 | WATER + MOUNTAIN | WATER | MOUNTAIN |
| W-09 | CLIMATE + AIR | AIR | CLIMATE |
| W-10 | CAPACITY | CAPACITY | * |

**经确认的裁决原则：权重规则绝对优先于命中条数。** 即当一个项目 GROUNDWATER 命中 2 条强制规则、MOUNTAIN 仅命中 1 条时，若 W-01 生效，主赛道仍判给 MOUNTAIN（系统修复优先于单项配套），但引擎会输出留痕：

> 权重规则 W-01 与命中计数相悖：GROUNDWATER 命中 2 条 > MOUNTAIN 命中 1 条，已按权重规则裁定 MOUNTAIN 为主赛道

保证可预测、可复现、可解释。

**兜底机制**：无权重规则覆盖时，单标签直接定主；多标签按强制规则命中条数定主；条数并列则标记 `FALLTHROUGH_MULTI_TIE` 进人工复核队列。**不强行裁定。**

**落地点**：`jev_rules.json` 的 `WEIGHT` 段、`jev_engine.py` 的 `_resolve_weight()`。

## 三、实测验证

规则引擎内置三组回归用例，全部通过：

| 场景 | 输入要点 | 主赛道 | 协同 | 人工复核 |
| --- | --- | --- | --- | --- |
| 废弃矿山 + 地下水监测井 | 矿山生态修复、监测井 3 座、边坡治理、渣场防渗阻隔 | 山水林田湖草沙生态修复 | 地下水污染防治 | 是（SOIL 无规则依据） |
| 仅管网建设 | 雨污分流管网 + "不涉及河湖水体治理" | 无（WATER 被剔除） | — | 是（规则冲突留痕） |
| 燃煤锅炉 + 减污降碳 | 超低排放改造、散煤替代、甲烷排放控制 | 大气污染防治 | 应对气候变化 | 否 |

**关键观察**：场景 1 中 GROUNDWATER 命中 2 条、MOUNTAIN 命中 1 条，主赛道仍判 MOUNTAIN，同时输出相悖提示 —— 权重规则绝对优先的设计意图得到验证。

## 四、输出规范修订

### 修订点 1｜取消"可信度 100%"表述

原方案的"判定可信度：100%（规则终审通过）"不可验证。**可信度不能由系统自称，只能由覆盖情况推导。** 改为输出三项可核查指标：

```json
"audit": {
  "rule_hit_count": 3,
  "by_label_hit_count": { "GROUNDWATER": 2, "MOUNTAIN": 1 },
  "weight_rule_applied": "W-01",
  "needs_human_review": true,
  "review_reasons": ["语义层给出但规则层无依据：SOIL"]
}
```

### 修订点 2｜字段命名统一

原方案步骤 3 与输出模板的七个字段名称、顺序不一致，对接数据库会字段错位。现统一为单一 JSON Schema（`result.schema.json`）：

| 字段 key | 中文名 |
| --- | --- |
| `support_directions` | 资金支持领域 |
| `key_project_types` | 重点支持项目类型 |
| `excluded_scope` | 禁止申报 / 不纳入支持范围 |
| `applicant_requirements` | 申报主体要求 |
| `funding_rules` | 投资比例 / 资金补助方式 |
| `performance_targets` | 绩效目标核心要求 |
| `applicable_region` | 适用地域范围 |

新增 `source`（文档层级闸门）与 `audit`（审计轨迹）两个顶层块。`Source.level` 限定 `国家级 | 省级`，非此层级直接拒收。

### 修订点 3｜全字段证据回指

每个字段值携带 `spans`（段号）与原文摘录，实现"有原文依据"的强制要求。文档预处理阶段切段编号（`P001`、`P002`…），此编号是所有证据的基础。

### 修订点 4｜负面清单独立校验

`excluded_scope` 采用 `items[]` 列表结构，逐条携带段号，便于做"零遗漏"的自动核对（对比原文否定句数量与提取条数）。

## 六、遗留风险与下一步

| 优先级 | 事项 | 说明 |
| --- | --- | --- |
| 高 | 规则池覆盖度不足 | 27 条强制规则远不足以覆盖真实指南。需用真实文档做回归，统计漏报率 |
| 中 | 否定作用域边界 | **已修**：作用域按句号/分号/换行截断，不跨句。同句内并列成分共享否定。复杂嵌套否定（"不属于以下情形：…"）仍可能漏判 |
| 中 | 同义词收敛 | 规则词表为人工列举，存在同义异形（如"尾矿库"vs"尾矿"）。建议加同义词映射层 |
| 中 | 表格与附件内容 | 申报指南的支持方向常以表格呈现，OCR 表格结构丢失会影响抽取 |
| 中 | 跨章节语义冲突 | 同一文档不同章节对同一事项表述可能不一致（如"支持"与"不予支持"并列） |
| 低 | 权重规则冲突检举 | 建议加规则自检，检测互斥的权重规则组合并在加载时报错 |

**关于"扩展规则库"**：本次未做。原因是规则词表应由**真实指南全文回归**驱动，而非凭常识臆造 —— 否则只是把幻觉从模型搬到了规则文件里。建议先收集 20-30 份国家级与省级指南作为测试集，跑出漏报/误报清单后再定向扩池。

---

## 七、一句话结论

**架构能不能用，不取决于 Prompt 写得多漂亮，而取决于规则层能不能脱离 LLM 独立判定、判定结果能不能复现、错了能不能追溯。**

本报告交付的版本在三点上都站得住；规则池的覆盖度仍需真实文档喂养，这是持续工程而非一次性交付。
